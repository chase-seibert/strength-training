# Architecture

## Shape

StrengthLog is a dependency-free SwiftUI app targeting iOS 17 and later. SwiftData owns local persistence, Swift Charts renders progress, and `AsyncImage` loads optional catalog photography.

The resting UI is organized around five tabs:

- Workout: available routines first, then paged four-week activity and a conditional Deleted Workouts restoration link.
- Routines: routine composition, naming, icon and color selection, ordering, and recoverable deletion.
- Exercises: catalog browsing and custom exercises.
- Progress: aggregate pounds volume and immutable session snapshots.
- Settings: a People section for configurable participant names/colors and archiving, plus app information.

In Debug builds, Settings also links to a Developer menu. Its default-off active-workout frame monitor toggle conditionally enables the diagnostic display link, overlay, and structured console samples; the disabled path creates none of them. Its replay action clears only the onboarding presentation flag. Onboarding then prefills existing people and routines while preserving workout history, exercise records, custom exercises, and all configuration. The menu and frame monitor are excluded from Release builds.

## Data flow

`Routine` owns only ordered exercise structure (`RoutineExercise` objects); it is independent of people and contains no workout weights, reps, sets, or customizable units. Units resolve from the saved master `Exercise` record in routines, open workouts, history, and progress. `ExerciseLog` resolves its stable exercise UUID with a bounded lookup and transiently caches the model (not its unit); the stored `unitRaw` is retained only as a legacy/orphan fallback, so no persistent schema change is needed. Tapping the exercise name in a workout pushes the existing exercise detail screen, where editing the master unit immediately updates the workout on return. Duplicated exercises retain independent master records and units. `WorkoutSession` owns the selected participant set and its per-person exercise logs. When a new session starts, participant selection comes from that routine's latest session, while each person's values are seeded from their latest matching exercise log across routines. Stable exercise IDs distinguish canonical exercises; case-insensitive names are used only when a legacy routine or exercise log lacks an ID. Legacy routine prescriptions remain a fallback when no matching session history exists. The active-workout screen keeps participant selection in a safe-area-inset header so it remains available while the exercise list scrolls. An optional `deletedAt` timestamp implements lightweight soft deletion: active-routine queries exclude deleted rows, while Deleted Routines can clear the timestamp to restore the same routine graph.

`PersonProfile.sortOrder` preserves the order established during onboarding across Settings, routine editing, workout setup, and participant visibility. The primary onboarding profile is therefore always presented first. Existing stores are migrated once using the original onboarding color sequence before persisting explicit order values.

Starting a routine immediately snapshots that graph into a persisted `WorkoutSession`. The start sheet defaults to the people from the most recent session and permits a quick subset toggle. Turning a person off only removes them from the session's visible participant set; their logs remain in the session so turning them back on is non-destructive. Session logs are independent objects, so changing a routine later does not rewrite exercise history; the current routine name is resolved from the session's stable `routineID` whenever history is displayed. During a workout the app edits session measurement, reps, completion, visibility, and sets directly. The active-workout screen fetches its catalog lookup and historical personal-record baseline once, retaining only lightweight values needed by the current session instead of observing the full catalog and workout history. Rapid load and rep edits mark the session dirty without synchronously saving the full SwiftData graph; persistence is checkpointed when a set completes, when the scene backgrounds, and when the workout screen closes. The active-workout UI presents left-filled, fixed-width participant Load and Reps columns followed by shared Remove Set and Add Set actions while retaining the underlying `WorkoutSet` records for history/import compatibility and allowing a remembered final-set override. Individual `WorkoutSet.isSkipped` flags support recoverable last-set skips without deleting the person's history; skipped sets are excluded from active completion and totals. Per-set completion remains sequential for each participant and wraps in two-wide rows; the shared actions add or remove the final set for everyone. The latest saved log for the same exercise is the next-time default source for each person's weights, reps, and completed-set structure across routines.

For exercises whose master equipment is `dumbbell`, completed set summaries retain the `per dumbbell` label. A persisted optional reminder setting on the master `Exercise` defaults from dumbbell equipment until explicitly overridden in Edit Exercise. When enabled for a weight-tracked exercise, any participant's active-workout callout can be tapped to switch every participant's display between the entered measurement labeled as the total for both arms and half that value labeled per arm. The tapped display state is transient per exercise card. Neither the setting nor the callout changes base or per-set measurements, history summaries, or training-volume calculations; the active load input uses a neutral accessibility label because the callout offers both interpretations.

Exercises whose sets cover both sides can use a separate master `Exercise` total-reps/per-side reminder. Its optional setting defaults on for the 76 catalog entries already reviewed as per-side, plus Russian Twist because its instructions alternate sides; it can be overridden in Edit Exercise. While enabled, the active reps picker stores total reps across both sides, and every participant's tappable callout switches between that total and an approximate per-side split (odd totals display a range). The display state is shared across participants on the exercise card and resets for a new card. Neither the callout nor its toggle changes any base or per-set rep value. Reminder-enabled logs use total-rep counting so volume is not doubled; legacy `perSide` counting remains available when the reminder is disabled.

Only one session can be open in the app UI. When one is open, the Workout navigation stack pushes its editor over Home and hides the tab bar. Home remains alive beneath that destination but replaces its content with an inert placeholder, preventing hidden timeline, query, and calendar updates during active-workout scrolling. Its activity grid also memoizes personal-record counts by workout-history revision so cell reevaluation never repeatedly traverses the full SwiftData workout relationship graph. Completing a session closes and saves it, snapshots a value-type `WorkoutCelebrationSummary`, and presents the full-screen celebration view before returning to the five resting tabs. The snapshot computes each participant's pounds volume, newly achieved personal records, and four-week workout/volume totals from saved history, so the celebration screen has no live SwiftData query of its own. Completed logs can be inspected from Workout's calendar, while Progress retains the explicit reopen action. The persisted `isActive` and `endedAt` fields remain as presentation and migration plumbing, not as workout completion or timing concepts.

Workout duration is one validated interval: active sessions use `now - startedAt`, completed sessions require `endedAt - startedAt`, and durations must be positive and no longer than 24 hours. The last completed set does not determine session length. Apple Health recording is an opt-in Settings preference, off by default. Enabling it requests workout write authorization only; after a successful local save at the explicit Complete Workout action, an enabled and authorized session with completed sets and valid timing asynchronously writes one traditional strength-training workout. A group session remains one record owned by the device's Health user; local deletion or disabling export does not remove existing Health samples. A Health permission or write failure never rolls back local completion or blocks celebration. Stable HealthKit sync metadata identifies the session for retry replacement.

An active timed exercise can store an independent optional start date, duration in seconds, and originating exercise ID on `WorkoutSession`. The five-second preparation countdown and its exercise ID and target are transient view state; only after preparation does the view save the active timer fields. The countdown is derived from the saved start and duration, so it continues through exercise navigation and workout resume without changing the routine's rest timer. Expiry clears the saved timer before routing through the shared set-completion path, then plays the in-app alert sound once. If expiry occurs while the app is suspended, the same expiry path runs when the workout becomes active; background alerts do not request notification permission. The view disables the system idle timer during both preparation and the active countdown. These optional SwiftData fields use defaults and allow lightweight migration of existing sessions.

Both `RoutineExercise` and `ExerciseLog` use explicit `sortOrder` values. Open-workout moves rewrite those values after every reorder. Routine edit mode instead snapshots its name, icon, color, and ordered exercise references into draft state: deletion, reordering, and appearance changes refresh that draft immediately, Cancel discards it, and Save applies relationship removals, child deletion, appearance, and final sort-order values in one persistence operation. Deleting the routine itself sets `deletedAt`, preserving its relationships and all independent workout history. A running workout can append catalog exercises with participant logs for the current workout crew; additions remain part of that session snapshot.

Fresh installs enter onboarding before the tab interface. Onboarding creates user-entered profiles and, only when selected, editable copies of the Upper Body, Lower Body, and Core starter templates. The same templates remain available from the Routines add menu, alongside custom routine creation. Existing stores containing profiles bypass onboarding.

Plank defaults to seconds and a 60-second target when no prior workout value exists. A one-off catalog correction changes the original bundled Plank record from reps to seconds on existing installs, without rewriting saved sets or repeatedly overriding later user edits. Timed exercises show one unit-labeled target control rather than load plus reps. Imported duration values retain canonical seconds, and time edits keep those values consistent with the displayed target. Existing numeric records, IDs, relationships, ordering, and completion state are preserved; changing between unrelated unit types corrects their interpretation rather than guessing a conversion.

The bundled catalog now includes `defaultDurationSeconds` for every seconds-based entry. It is decoded once and looked up by stable source ID, with original-name fallback for duplicates/legacy records. These immutable defaults do not add fields to the SwiftData schema. `Exercise.defaultTarget` uses this metadata only for seconds, falling back to 30 for custom timers; other units retain their existing behavior. Saved history and legacy prescriptions still take precedence over fresh defaults. Static holds generally start at 30 seconds, with reviewed 10/15/20-second exceptions from their instructions. The six reviewed balance/rope/climber/isometric corrections and three seconds-to-reps corrections use a separate one-off migration flag, set only after saving. Only noncustom, nondeleted source records still matching the known old unit are changed; later edits are not reapplied. The existing data cannot distinguish an intentional choice of the old default from an untouched default. Persistence tests cover all nine corrections, catalog targets, custom unit choices, preserved set values/IDs/order, and reopening the store.

### Rep counting

`Exercise.repCountingMode` is a typed `standard`/`perSide` value backed by the nullable
`repCountingModeRaw` SwiftData attribute. Only legacy nil fields receive catalog
initialization; explicit choices are never overwritten. Exercises with the total-reps/per-side
reminder use total counting regardless of this legacy field; with that reminder off,
`ExerciseLog` resolves the chosen mode from the master model, including mid-workout edits
and history. There is no per-routine or per-workout copy. Timed and distance exercises
ignore this rep-only setting.

Legacy `perSide` targets remain the number entered: 7 per side means 7 left + 7 right,
with one set completion after both sides. Shared pounds-volume calculations multiply
legacy per-side reps by two. Reminder-enabled targets are already the total across both
sides, so their volume uses the entered count without a multiplier. PRs are derived from
completed history rather than persisted, so changing an exercise's counting setting
re-evaluates existing logs without rewriting saved reps. See
[the reviewed defaults](rep-counting-defaults.md) for the 77 default-on reminder choices.

`make rep-counting-ui-test` runs live master-edit and disk-persistence checks. A Debug-only
`-repCountingMigrationFixture` flag opens a separate named store and compares saved IDs,
relationships, sort order, counts, targets, weights, and completion flags against a
pre-change binary's snapshot; it never opens or resets the user's normal database.

## Hevy CSV import

StrengthLog registers `public.comma-separated-values` as a document type and routes both shared files and the Settings file picker through `HevyImportCoordinator`. `HevyCSVParser` is an RFC 4180-style, dependency-free parser that normalizes mixed CRLF/LF line endings and accepts the Hevy workout columns shown in the product flow, including local or ISO timestamps, pounds or kilograms, miles/kilometers/meters, duration, set type, and RPE. The first `title` column is treated as the routine name; rows are grouped into workouts by title and start time, then into ordered exercises and sets.

Before persistence, the user selects which source routines to import. Only exercises and workouts belonging to those routines proceed. Every distinct relevant exercise is visible in the review UI and resolves through a remembered `ExternalExerciseMapping`, normalized catalog-name scoring, or an explicit local/custom choice. Unmapped exercises are skipped in both routine templates and history. Confirmed mappings are reusable on later imports. A Hevy account is assigned to one selected `PersonProfile`.

The importer always creates a new routine for every selected source title and never updates an existing one. Name collisions receive a numeric suffix. Each routine includes the union of mapped exercises found across all exported workouts for that title; units come from the mapped catalog exercise. As a secondary operation, the importer snapshots selected workouts as inactive history, retains per-set load, reps, distance, duration, RPE, type, notes, and superset identifiers, and uses a stable source key to skip re-imported workouts. All inserts and mapping updates are saved together; a failure rolls back the model context.

## Catalog

`exercise-catalog.json` is a generated, normalized, offline seed. On first launch it becomes editable SwiftData `Exercise` records. Each source record retains both image paths; the app maps those paths to a bundled 640-pixel WebP derivative and pages through the local images in the library and active workout. Thumbnail file reads and display preparation happen off the main actor, with decoded images retained in a bounded in-memory cache so newly visible workout cards do not synchronously decode WebP files during a flick. Custom exercises use the same model and have no source identifier.

Every exercise has an immutable record UUID, a never-changing `originalName`, and a `rootExerciseID`. Renaming mutates only the display name and updates cached names on routine and workout references while retaining their UUID link. Duplicating creates a new custom record UUID but copies the canonical root UUID and original name, so copies remain traceable to the same source family without becoming the same editable record. `RoutineExercise` and `ExerciseLog` both carry the concrete exercise UUID; name matching remains only as a legacy-store fallback, and seed maintenance backfills unambiguous legacy references.

## Tradeoffs

- Participant references are snapshot names rather than mutable foreign keys. This intentionally keeps history readable after a profile rename or archive.
- Latest-value seeding follows the stable master exercise ID across routines, with case-insensitive name fallback only for legacy records without an exercise ID. A later migration should store the routine-exercise UUID in each exercise log if two references to the same master exercise need independent history.
- The first seed inserts 873 records on the main model context. It passed the first-launch smoke test, but a background staged import would be appropriate if the catalog grows substantially.
- Sync, outbound sharing, live superset behavior, and cloud backup are outside the first version. HealthKit workout export is supported for explicitly completed sessions.
