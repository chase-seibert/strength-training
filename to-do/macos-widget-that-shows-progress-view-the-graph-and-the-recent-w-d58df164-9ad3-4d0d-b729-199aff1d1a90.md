## User requirements

- As a user, I want a widget on my Mac showing the Progress training-volume graph, so that I can see my training trend from the desktop or Notification Center.
- As a user, I want recent workout history with the number of personal records (PRs) for each workout, so that I can see recent activity and achievements together.
- As a user, I want the widget to agree with the app and identify when its data was last updated, so that I can trust the displayed progress.

Problem: `StrengthLog/ProgressView.swift` already provides the graph and history, but `StrengthLog.xcodeproj/project.pbxproj` has only iPhone app, UI-test, and Live Activity targets. There is no ordinary progress widget, Mac app, App Group entitlement, or cross-device workout synchronization.

Delivery assumption: implement an iOS WidgetKit widget that macOS displays through Apple's “Use iPhone widgets” feature. This uses the existing phone data without introducing a separate Mac database or sync service. It requires macOS Sonoma or later, iOS 17 or later, the same Apple Account, the phone nearby or on the same Wi-Fi network, and the Mac setting enabled. Apple documents [iPhone widgets on Mac](https://support.apple.com/guide/mac-help/add-and-customize-widgets-mchl52be5da5/mac). Independent native Mac operation remains a decision to resolve before implementation; if required, revise the architecture for a minimal native Mac host plus an explicitly designed data-transfer mechanism.

Initial layout assumptions: medium and large widgets both show a compact graph and history; reserve two history rows in medium and up to five in large. Use the app's default rolling 12-week range and all its participant series. Keep PRs in combined trophy/count history badges, with no PR annotations on graph points. Hide the badge for zero, matching Progress. Additional sizes, range configuration, workout editing, reports, and a full Mac app are outside this initial scope.

This turn creates only this plan. It does not implement, build, deploy, commit, or change task completion.

## Architecture and data model

**Reuse existing calculations.** Extract the weekly aggregation, range handling, participant ordering/colors, and history presentation values from `ProgressView.swift` into a testable summary builder with explicit date/calendar inputs. Keep weekly volume in `lb × reps`, using `ExerciseLog.completedPoundsVolume(for:)` from `Models.swift`; kilograms and non-weight units currently contribute no pounds volume. Preserve the current treatment of non-deleted sessions, including saved active sessions and their completed sets. Do not silently redefine the graph as completed-workouts-only.

Calculate `PersonalRecords.achievements(in:)` once over the entire non-deleted history, group by session ID, then select recent rows. Restricting the PR baseline to 12 weeks would invent records. Preserve completed/non-skipped set filtering, active participant selection, exercise UUID identity with legacy name fallback, strict improvement over previous values, and one achievement per person/exercise/workout. Per-side volume and weighted PR values have different rules; reuse both unchanged. Resolve routine names and profile colors/order as Progress currently does, including its missing-record fallbacks.

**Share a derived snapshot.** Add a versioned, Codable `ProgressWidgetSnapshot` and a small snapshot-store interface shared by the app and widget. Include generation time, calendar/time-zone metadata, range bounds, participant series, weekly points, and at most five history rows containing session UUID, routine title, start time, set counts, and PR count. For rolling-window expiration while the app is closed, retain bounded per-session volume summaries within the 12-week window so the provider can remove expired contributions and reaggregate; never include the complete set graph.

The phone remains the sole writer of an atomically replaced snapshot file in an entitled App Group, provisionally `group.com.cseibert.StrengthLog`. The widget reads this cache without opening or mutating SwiftData. No authoritative model/schema migration is required. Explicitly preserve the existing app-local store location when adding the entitlement: audit the default `ModelConfiguration` in `StrengthLogApp.swift` and disable automatic App Group store selection for the authoritative database. Verify the same database URL and records across upgrade. An App Group shares local storage between app and extension; Apple's Continuity transports the rendered widget to Mac. It does not synchronize a Mac database.

**Publish after durable changes.** Add a coalescing publisher that reads committed data in its own SwiftData context/actor and passes only immutable values across actor boundaries. Publish on initial startup/foreground reconciliation and after successful saves affecting sessions, imports, deletion/restoration, routine names, people presentation, or master exercise units/rep-counting. Cover `StrengthLogApp.swift`, `ActiveWorkoutView.swift`, `ProgressView.swift`, `HomeView.swift`, `HevyImportView.swift`, `RoutinesView.swift`, `SettingsView.swift`, and `LibraryView.swift` through a shared invalidation mechanism. Preserve deferred workout saves; do not scan history on every tap or render. Serialize publication so an older calculation cannot overwrite a newer snapshot. Save failures must not publish unsaved values.

**Widget lifecycle.** Add an ordinary `StaticConfiguration` widget and `TimelineProvider` alongside `LiftChaseLiveActivityWidget` in the existing extension bundle. The provider loads the snapshot, handles placeholders/empty/error states, expires rolling-window data at scheduled boundaries, and requests reasonable refreshes. After a successful changed snapshot write, reload only the progress widget kind. WidgetKit and Continuity control delivery timing; show the snapshot's update time rather than promising live refresh. Retain an explicitly dated last-good snapshot on publication failure; missing/corrupt/unsupported snapshots must show an unavailable/setup state, not invented zero history. App Group failure must surface in the app without interrupting workout persistence.

## Basic test cases

- Representative history: widget weekly points and recent rows match Progress at a fixed date/calendar; rows are newest first, names/colors agree, and chart has no PR-point badges. Reuse the 114-workout sanitized fixture in `Resources/pr-sticker-phone-history-fixture.json` and its expected per-workout PR counts.
- PR boundaries: an older workout outside 12 weeks still sets the PR baseline; tied values, incomplete/skipped sets, disabled participants, repeated improving sets, and duplicate display names with distinct exercise UUIDs produce the existing counts.
- Volume boundaries: standard/per-side pounds values match existing calculations; kilograms, duration, and reps-only workouts can have history/PRs without pounds-volume points. One point, zero volume, and many participant series remain readable.
- Empty/expiration states: new install, no workouts within the range, and workouts expiring while the app is closed show honest empty states; week boundaries, daylight saving, locale, and time-zone changes use consistent bucketing.
- Updates: complete/save an active workout, import history, delete/restore an old PR-setting workout, rename a routine, change participant colors/order, and edit master units/rep-counting. The next published snapshot reflects every change, including recalculated later PRs. A failed save leaves the previous snapshot intact.
- Reliability: app relaunch preserves history; enabling App Groups preserves the old database URL, IDs, relationships, and counts. Concurrent rebuild requests cannot regress the snapshot. Missing group access and truncated/unknown-version snapshot files produce recoverable unavailable states.
- Mac acceptance: add both widget sizes to desktop and Notification Center; graph, history, badges, and update time remain legible in light/dark and monochrome appearances, with long titles and VoiceOver. Phone disconnection leaves dated data; reconnection permits refresh. Clicking must respect Apple's phone-continuation behavior and must not claim to open a nonexistent Mac app.
