# Task #153 — AI coaching and weekly reports

Plan only. Project: `1b066122-1007-43ba-bd6b-6ea2ef9663ab`. Task: `10f9cc9f-55cf-4411-a74e-f1c90a91717e`. No application changes are authorized by this document's creation.

## User requirements

- As a user, I want coaching about my overall regimen across the routines and exercises I am actively working on, so that it can help me decide what to do next.
- As a user, I want the coaching to consider the workouts I have completed since I last generated a report and assume I will continue that pattern, so that suggestions reflect my actual current regimen.
- As a user, I want to choose on-device models or the OpenAI API, so that I control where coaching is generated and whether workout context leaves my phone.
- As a user, I want a Lift Coach preview I can reopen from the developer menu, so that I can review the proposed experience anytime.
- As a user, I want Lift Coach to suggest workouts that are a step up from what I currently do when I am maxing out the prescribed sets and reps, so that I can choose an appropriate progression.
- As a user, I want Lift Coach to suggest progression exercises I am not currently doing, explain why each is a step up, and show what it could replace in my routine, so that I can judge and try a useful change.
- As a user, I want Progress to show my training-volume graph first, followed by Lift Coach content and a short workout history, so that progress and coaching live together in a scrollable view.
- As the primary user, I want Lift Coach and recent workout history focused on my workouts with no person selector, while the volume graph keeps separate series for all participants.
- As a user who has not generated coaching yet, I want Progress to keep its existing graph/history content and show a friendly “learning your habits” illustration, so that I know coaching will appear after I log more workouts.
- As a user, I want the weekly report notification to open this Progress experience, so that I can read the report and coaching alongside my graph and recent workouts.

**Clarified scope:** The product name is “Lift Coach.” Coaching is regimen-level, not an in-workout next-exercise or next-session prescription. Establish the baseline from the most recent generated report (or a documented first-report baseline); summarize subsequent completed workouts across the user's active routines and exercises, and assume continued participation in those routines. When completed workouts show the user has reached the configured set count and top rep targets, surface optional workout/routine ideas that are a measured step up from the current work. The user chooses whether to try them; coaching does not silently mutate saved routines, targets, sets, or history. Do not add form tips or form assessment. The mockup is a planning deliverable and the Developer Menu links to sample views of both Progress states; it is not a separate production mockup screen. The real Progress tab remains useful before and after generation: it starts with the shared participant volume graph and a “learning your habits” illustration, then replaces that coaching placeholder with the generated Lift Coach content once available. Lift Coach and brief recent workout history focus on the primary user; the chart shows all participants and there is no person selector. The weekly notification opens Progress at the generated report/coaching content.

**Latest implementation clarification:** Preserve the app's visual style while using the mockups for layout and content. The Progress volume graph shows each active participant as a separate profile-colored series with a legend; Lift Coach and recent history remain primary-profile scoped. On weekly report generation, request structured sections from either Foundation Models or OpenAI for overall pattern, what's next, exercise progression, and rest assessment. Compute workout/set/volume/duration pills, routine counts, and daily volume locally from workout history. Only suggest an exercise from a reviewed progression relationship after the current exercise has met all prescribed set/repetition/load targets in two recent sessions; the suggestion must be absent from active routines and recent history. Rest assessment uses the configured rest target, RPE, and target performance, and must say when evidence is insufficient because exact rest intervals are not recorded.

Proposed defaults, subject to product review: Apple Foundation Models as the first on-device provider; explicit OpenAI opt-in with a personal API key stored in Keychain; weekly report/notification cadence configurable to the user's local week. AI remains off until a provider is chosen. The Progress report/coaching experience is scoped to the primary user; remote requests include only that user's permitted context. A public app credential/backend strategy remains a separate decision before distributing cloud access.

## Architecture and data model

**Existing foundations.** The app targets iOS 17 and uses a local SwiftData `ModelContainer` in `StrengthLogApp.swift`. `Models.swift` holds exercise instructions, notes, stable exercise IDs, workouts, participant logs and sets. `ActiveWorkoutView.swift` already tracks the current exercise and presents `ExerciseDetailView` from `LibraryView.swift`. `ProgressSummary.swift`, `PersonalRecords`, and `WorkoutCelebrationSummary` provide established volume/record semantics. `ProgressView.swift` already scrolls with a volume chart and workout history. Keep all participants on separate chart series; scope Lift Coach and recent rows to the primary profile. Retain the date-range control and omit a person selector. `SettingsView.swift` contains the Debug-only `DeveloperMenuView` and a repeatable celebration preview. `LiveActivityManager.swift` schedules rest notifications; there is no coaching provider, report store, or notification response router yet. The existing application/scene delegates in `KidsWatchShareAcceptance.swift` handle watch activation and CloudKit share acceptance; preserve these paths.

**Read-only regimen coaching pipeline.** Introduce value-type `CoachingContext` and a small `CoachingProvider` interface with on-device, OpenAI, and deterministic preview implementations. Resolve the first non-archived profile by `sortOrder` as the primary user and use that profile's most recently generated report as the analysis baseline, then summarize completed workouts after its generation cutoff across all routines and exercises the primary user is actively using. Describe recurring routine/exercise frequency, recent performance/load/reps/volume trends and gaps using the app's existing tracking semantics. The coaching asks what the user should continue, sustain, or review next, assuming they will keep doing the observed regimen. It does not focus on the next unfinished set or prescribe a new next session. Calculate the underlying facts in Swift; the model explains them with references to source report/session/exercise IDs. Keep raw SwiftData objects on their owning actor; pass bounded immutable snapshots to asynchronous generation.

**Progression ideas.** Compute readiness to progress deterministically from the saved routine prescriptions and completed workout history before asking a model to explain options. An initial observable rule is that every prescribed set reached its configured reps in two consecutive completed sessions for the primary profile and exercise; tune this threshold if product review establishes a better rule. Only then offer clearly labeled, optional workouts to try next. In addition to small load/rep/set increases, suggest reviewed progression exercises from the bundled catalog that the person is not currently doing (exclude exercises in active routines and those logged since the report baseline). Maintain an offline reviewed progression relationship keyed by stable catalog `sourceID` values from the current exercise to the candidate so Lift Coach can explain why it is a step up; seed and curate these links alongside the bundled exercise catalog and keep them versioned. Do not let generated text invent the relationship. Show the evidence from qualifying workouts, the progression rationale, the current routine/exercise that could be replaced, and a preview of the resulting workout. Candidate exercises must be absent from active routines and workouts since the last report. Suggestions do not count as performed workouts or change a saved routine; the user reviews and explicitly saves a suggested workout as a new routine or chooses to replace an exercise in an existing routine.

Use concrete exercise UUIDs, not display names or shared `rootExerciseID`, to distinguish duplicates. Prefer `ParticipantLog.personID`; use snapshot-name matching only for unambiguous legacy records, with ambiguous records left separate. Existing progress/PR helpers often group by name, so reuse their arithmetic carefully rather than treating them as an identity-safe participant join. Honor active participant membership, per-set measurement overrides, completed/non-skipped sets, total-reps/per-side conventions, and time/distance units. Never reinterpret all measurements as weight. Limit history/context size and do not traverse the entire store during scrolling or SwiftUI body evaluation.

Keep a bounded coaching result keyed by primary profile ID and last-report ID/cutoff, provider, prompt version and regimen input fingerprint. Cancel obsolete requests and discard late responses after the primary profile, baseline, provider, or source history changes. No generation on every keystroke or render. Users request generation explicitly; repeated taps coalesce into one in-flight request. Distinguish loading, ready, cached, unavailable, refused and failed states; deterministic regimen statistics remain viewable when narrative generation is unavailable.

**Providers and privacy.** Availability-gate the Foundation Models adapter on supported OS versions and runtime model readiness; preserve the app's iOS 17 minimum. An unavailable model explains the reason and offers original instructions/settings rather than silently sending data to OpenAI. Apple's documentation identifies `SystemLanguageModel` as the on-device model and calls for availability checks. Verify exact SDK symbols and supported languages during implementation. [Apple Foundation Models](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models)

For OpenAI, use a cancellable `URLSession` client and the Responses API with bounded input/output, schema-constrained `text.format`, and `store: false`. Validate parsed output and source IDs; handle refusals, incomplete output, auth failures, quota/rate limits, offline state and timeouts. Select and test a suitable available model during implementation rather than fixing an unverified model name here. Do not interpret disabled response storage as a promise of zero provider retention. [Official Responses API guidance](https://developers.openai.com/api/docs/guides/migrate-to-responses#additional-differences)

Show what context will be sent before enabling cloud coaching. Omit participant names and unrelated people; use request-local aliases and allow private notes to be excluded. User-entered notes/instructions are data, not privileged model instructions. Credentials belong only in Keychain, never source, UserDefaults, diagnostics, fixtures or report payloads. Provide replace/remove controls. Do not include a shared developer API key in a distributed binary. Bound retries and generation frequency; no unattended cloud polling or requests from demo previews. Generated text cannot execute actions or update workout data. Reject unsupported numeric claims and retain factual statistics if narrative validation fails.

**Weekly report persistence.** Add an app-owned `WeeklyCoachingReport` SwiftData model and repository. Store stable report UUID, primary profile ID, week start/end and timezone/calendar policy, creation/update timestamps, deterministic metrics payload, versioned structured coaching sections, provider/model/prompt version, input fingerprint, and generation status. Keep workout count, completed sets, pounds × reps volume, workout duration, routine frequency, and daily volume locally computed. Use a versioned payload with queryable primary-profile/period fields and idempotent lookup/upsert so relaunch or simultaneous requests cannot create duplicate reports. The report is derived data; original workout records remain authoritative. Add the model to the app schema with an explicit migration version/baseline strategy and verify upgrade from an existing store; never reset user storage on failure.

For the report's weekly view, include the primary user's completed, nondeleted sessions in its explicit half-open calendar-week interval. Retain a last-generated-report cutoff for primary-user regimen coaching: its input includes all eligible workouts after that cutoff, potentially spanning multiple weeks, across the primary profile's active routines/exercises. A newly generated weekly report advances that cutoff only when its facts and report record are successfully saved; merely opening, previewing, or receiving the notification does not. Show workout count, completed sets, existing pounds-volume metric with its label, valid duration and exercise/routine highlights; display time/distance activity separately from volume. Compare weekly totals with the preceding complete week; a zero/missing baseline produces “No prior comparison,” not infinity or invented gains. PRs require the appropriate earlier baseline, not just the current week's maximum. Provide an empty report without invented commentary. If no workouts exist yet, keep the training-volume section at the top with a no-data state, followed by the learning-habits card and an empty recent-workout section. Build facts on foreground reconciliation and when opened; opening an old report does not automatically incur another API charge. History import/edit/delete/restore invalidates affected source fingerprints; refresh deterministic facts and mark old narrative stale until regenerated. Old narrative must not continue to cite removed workouts.

Preferences for provider and notification opt-in/schedule belong in UserDefaults. Resolve the primary user from the first non-archived `PersonProfile` in existing `sortOrder`; do not add a profile picker to Progress. Saved reports belong in Application Support via SwiftData; ephemeral cue caches remain separate. No change to workout logging schema semantics or new cloud sync is required. Audit existing backup/export coverage when introducing reports, and distinguish regenerable report data from authoritative workout history.

**Notification and navigation.** Introduce a weekly notification coordinator with its own request/category identifiers, separate from the rest timer. Request permission only when the user enables reminders; show denied status and a Settings route without repeated prompts. Schedule a repeating calendar notification with neutral wording such as “Review your training week,” avoiding a claim that AI commentary is already ready. Local calendar triggers are supported by UserNotifications. [Apple local notification guidance](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)

On response, resolve the referenced weekly report and open the Progress tab positioned at its report/coaching section, preserving the graph above and recent workout history below. Queue the route until the model store is ready. A delayed tap opens that stable report period; if it is unavailable, show the latest Progress state and refresh deterministic facts. Reconcile timezone/day/time changes and cancel only weekly requests when disabled. Exact background AI generation is not a prerequisite for reminder delivery; background refresh, if later added, is an optimization.

Install a retained `UNUserNotificationCenterDelegate` through the existing application delegate. Queue cold-start routes until the model store and onboarding are ready, then open the report through an app navigation coordinator. Preserve active workout state and return navigation when a report opens over training. Keep the existing `.onOpenURL` Hevy import handling, CloudKit share acceptance and rest notifications functioning. The same report and generated Lift Coach content remain reachable by scrolling Progress when permission is denied or delivery is delayed by system settings.
