## User requirements

- As a user, I want saving a reordered active workout to also save that order to its routine, so that future workouts started from the same routine use my chosen exercise sequence.
- As a user, I want Cancel to discard the draft and saved reordering to preserve my recorded sets, so that changing the sequence does not lose workout progress.
- Scope: extend the existing compact Reorder Exercises screen and Save operation. Keep other routines, completed workout snapshots, exercise contents, participant settings, and load/rep defaults unchanged. No new routine-version feature is needed; “future versions” is interpreted as future sessions started from the existing routine.
- Assumption: Save updates the routine immediately, even if the active workout is later abandoned. Do not defer this change until workout completion or add a persistence toggle.
- This turn is planning only. Create or modify only this reserved plan; do not implement, run app builds, deploy, commit, or change the task completion flag.

## Architecture and data model

Current flow: `ActiveWorkoutView.swift` opens `WorkoutExerciseReorderView(session:)`, which keeps draft rows identified by `ExerciseLog.id`. Save calls `WorkoutSession.saveExerciseOrder(_:in:)` in `Models.swift`. That method validates session membership, updates only session `sortOrder` values, saves once, and restores them on failure. The footer explicitly says changes apply only to this workout.

`WorkoutSessionStarter.start` in `RoutinesView.swift` constructs new logs from `routine.exercises.sorted(by: sortOrder)`. Updating existing `RoutineExercise.sortOrder` values therefore makes future sessions inherit the saved sequence. `ActiveWorkoutView.activeRoutine` already resolves `session.routineID`; the add-exercise sheet already updates both session and routine.

No material architecture, storage schema, or migration change is required. Keep SwiftData, the stable routine ID, and independent routine/session children. Put the coordinated persistence operation in the model layer rather than saving each graph separately in SwiftUI. Retain the session-only API for its existing completed-history smoke test; add an explicit operation for saving active-session and routine order together.

The two graphs have different child UUIDs. Validate draft IDs against session log IDs, then map those logs to existing routine entries by catalog `exerciseID`. For legacy entries, allow a case-insensitive name match only when at least one catalog ID is absent and the mapping is unique. Never match two differing nonnil catalog IDs by name, and never use dictionary construction that can trap on duplicate catalog identities.

Recommended boundary policy, an assumption rather than an additional user requirement: require a live, nondeleted owning routine and an unambiguous one-to-one mapping of its entries to the session for coordinated Save. If the routine is missing/deleted, membership differs, or duplicates make matching ambiguous, show an actionable error and change neither order; do not silently claim future persistence or recreate removed entries. Check for changes since the reorder screen opened, including routine membership/order, before applying a stale draft. Cancel and reopen can refresh a stale draft; a lasting membership mismatch needs reconciliation through existing routine editing. This intentionally avoids inventing merge behavior for old session snapshots.

Validate everything before mutation. Capture both sets of original sort orders, assign contiguous positions to existing children, and persist through one `ModelContext.save()`. Restore both orders on failure while preserving unrelated pending load/rep edits; avoid a whole-context rollback. Dismiss only after successful persistence and use the existing alert for failures. Preserve log, participant, set, and routine-entry identities and all non-order fields. Preserve a no-movement Save as a no-op rather than overwriting a separately changed routine.

## Basic test cases

1. Start a three-exercise routine, record a set, move the last exercise to first, and Save. The active workout and routine detail both show the new sequence. Finish the workout and start the same routine: the new session has that complete sequence with fresh logs and normal defaults.
2. Drag and Cancel. Session and routine retain their original sequences; the next workout does too. Save without moving anything leaves both orders unchanged.
3. Save, close/resume, and reopen a disposable disk-backed store. Both orders persist, and original set IDs, measurements, reps, completion/skipped flags, and participant records remain unchanged. A historical session and another routine using the same exercises retain their prior orders.
4. Add an exercise through the existing active-workout add flow, then reorder and Save. It occurs exactly once in both graphs and in the next session. Rename a catalog exercise without changing its ID: matching still works. Unique legacy name-only entries also work.
5. Reject incomplete/repeated/unknown draft IDs, ambiguous duplicate matches, differing catalog IDs with identical names, and routine/session membership changes. No partial order changes occur. Missing/deleted routines produce an explanatory error without recreating the routine.
6. Change routine order or membership while a reorder draft is open. Save rejects the stale draft; reopening refreshes it. Force a persistence failure through a narrow test seam: both in-memory orders are restored, unrelated unsaved workout edits survive, and the screen remains open for retry.
7. With fewer than two exercises, retain the disabled Reorder action. For longer lists and larger text, retain scrolling, numbered positions, native handles, and accessible Save/Cancel controls; the footer describes current and future routine workouts.
