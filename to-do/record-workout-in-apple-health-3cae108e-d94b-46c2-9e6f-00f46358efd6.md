## User requirements

- As a user, I want a workout I explicitly end in StrengthLog recorded in Apple Health, so that my strength-training history is available alongside my other Health workouts.
- As a user, I want workout duration calculated from when I start the workout until I end it, so that the active timer, completed workout history, summary, and Health record agree.
- As a user, I want invalid or missing workout timing rejected and an unended workout omitted from Apple Health, so that Health does not receive a fabricated or misleading workout.
- As a user, I want Health authorization or save failures to leave my local workout usable, so that Health integration does not put my workout history at risk.

Assumptions: tapping Complete Workout is the explicit end action and triggers an attempt to save one traditional strength-training Health workout. While active, elapsed workout length is the current time minus startedAt; once explicitly ended, it is endedAt minus startedAt. Use this same workout-length calculation everywhere the app displays workout duration and when creating the Health sample. Rest and exercise countdowns have their own configured/target durations and are not workout-length calculations. Request only authorization needed to write workout samples; do not read Health data or invent active energy or other metrics. Keep the existing assumption that a session with no completed sets is not exported. The task does not specify an opt-out setting, multi-participant ownership semantics, or whether deleting a StrengthLog history item should also delete its Health sample; resolve these before implementation.

## Architecture and data model

HealthKit is not currently integrated; the architecture documentation lists it as outside the first version. WorkoutSession is the local source of truth and contains startedAt, endedAt, participants, exercises, and completed sets. StrengthLogApp.completeAndDismiss(_:) is invoked from the explicit Complete Workout action and closes/saves the session before building the celebration summary. Use this explicit completion boundary for Health export; do not export merely because a session is inactive, deleted, or has an endedAt timestamp.

Centralize workout-length calculation on WorkoutSession (or an equivalent shared value helper): for an active session, calculate from startedAt to now; for an explicitly ended session, require endedAt and calculate endedAt minus startedAt. Replace the current completed-duration preference for lastSetCompletedAt and align ActiveWorkoutDurationLabel, home/resume/history displays, and WorkoutCelebrationSummary with this shared rule. Last-set completion time remains useful for set history but must not define workout duration.

Sanity-check both timestamps and the resulting interval before display/export: require a valid start, a nonmissing end for a completed Health export, end strictly after start, and a positive finite duration within a documented practical upper bound. Return no duration for invalid completed timing; do not clamp negative values to zero or substitute the last completed set, current time, or another estimate. Agree and document the upper bound during implementation. An active session may continue showing a valid start-to-now elapsed duration, but it is never eligible for Health export until the explicit end action supplies a valid end.

Add a small HealthKit recorder/service that accepts a completed session snapshot and creates one HKWorkout of traditional strength training through HKHealthStore. Require both explicit completion flow and a valid shared completed duration before saving. Request workout write authorization only. Declare the HealthKit capability and required Health update usage description in the app target configuration. Keep HealthKit errors separate from SwiftData persistence and celebration flow; denial, unavailability, or save failure must not undo local completion.

No SwiftData schema or migration is required if HealthKit remains an external destination and the existing session ID is stored as sample metadata for retry deduplication. Confirm metadata support and authorization behavior on supported iOS versions. StrengthLog supports multiple named participants in one session while Apple Health belongs to the device's app user; whether to export that group session as one personal record is an unresolved product choice. The current model has no per-participant Health identity.

## Basic test cases

- While a workout is active, all workout-length UI uses the shared start-to-now calculation; independently configured rest and exercise countdowns continue to use their own durations.
- Complete a valid session with completed sets while Health write access is authorized; Apple Health receives one traditional strength-training workout whose interval and duration equal the shared start-to-end workout duration, and local history and celebration show that same duration.
- Attempt Health recording without an explicit Complete Workout action or without endedAt; no Health sample is written even if the session has sets or another code path marked it inactive.
- Provide a missing/invalid start, end equal to or earlier than start, non-finite interval, or interval beyond the documented maximum; completed duration is omitted and no Health sample is written rather than clamping or estimating.
- Decline Health authorization, make HealthKit unavailable, or simulate a write error; local completion and celebration still succeed without a crash.
- Retry recording the same explicitly completed session; its stable session identifier prevents a duplicate Health workout.
- Delete a session before completion or complete it with no completed sets; neither case writes a Health workout.
- Complete a multi-participant session and verify the chosen single-record behavior; do not create one sample per displayed participant unless product direction explicitly changes.
- Verify no active-energy, heart-rate, or other unsupported measurements are written and existing local workout data remains unchanged.

## High-level implementation details

1. Confirm first-use authorization, automatic recording versus a Settings opt-out, multi-participant handling, Health sample deletion behavior, and a reasonable maximum workout duration for sanity validation. Preserve the user's explicit-end requirement regardless of how other UI is resolved.
2. In StrengthLog/Models.swift, define one validated workout-duration calculation for active and completed sessions. Active sessions use now minus startedAt; completed sessions require endedAt and use endedAt minus startedAt. Reject invalid, nonpositive, non-finite, or over-limit intervals without clamping. Remove lastSetCompletedAt as the duration endpoint.
3. Update every workout-length display and summary to call that shared calculation, including ActiveWorkoutDurationLabel, home/resume/history, and WorkoutCelebrationSummary. Verify completed legacy records use their explicit endedAt and that invalid records omit duration gracefully. Leave rest/exercise countdown calculation independent.
4. Add the HealthKit capability and a plain-language NSHealthUpdateUsageDescription. Implement a focused HealthKitWorkoutRecorder (or equivalent) that creates one traditional-strength HKWorkout from an explicitly completed session with a valid shared duration. Pass the stable session UUID in metadata for retry deduplication; export no incomplete/deleted sessions and infer no calories.
5. Integrate the recorder at completeAndDismiss(_:) in StrengthLog/StrengthLogApp.swift after local close/save, preserving the existing celebration transition. Ensure authorization or Health save work cannot stall or fail local completion. Recheck deleted-session paths cannot reach this recorder.
6. Add focused tests for active and completed duration consistency, start/end boundaries, invalid and too-long intervals, no end/no export, authorization denial, unavailable HealthKit, save failure, and duplicate prevention. Use an injectable HealthKit boundary for deterministic cases; verify an authorized completed workout appears once in Apple Health on a capable simulator or device. Follow repository workflows such as make lint and the relevant build/UI verification during implementation.
7. Update docs/architecture.md, product requirements, and setup/privacy documentation to describe the shared duration rule, explicit export boundary, requested permission, and deletion behavior. The main risks are permission-state ambiguity, retry deduplication, multi-participant ownership, legacy session durations changing from last-set to end time, and accidental exports from inactive/deleted sessions.
